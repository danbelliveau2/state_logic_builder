# JARVIS Benchmarks

Archived L5X outputs used to track generation quality across JARVIS versions.
Produced by `scripts/jarvisBenchmark.cjs`, which runs the exact same code path
as `POST /api/generate` (promptBuilder -> Claude -> validator, with self-repair).

## Layout & naming scheme

```
benchmarks/
  {project}/                              one folder per project JSON (basename, no .json)
    {smName}__jarvis_v{version}.L5X       JARVIS output for one state machine
    {smName}__jarvis_v{version}.report.json   validation results, attempts, edit plan,
                                               duration, token usage, cost estimate
    {smName}__jarvis_v{version}.ir.txt    the Intermediate Representation the model
                                          received (engineer-reviewable: devices,
                                          states w/ assigned numbers, transitions)
    {smName}__oldgen_current.L5X          old rule-engine exporter output (era A data point)
    __oldgen_april2026_baseline.L5X       historical baseline (see below)
    __jarvis_v0_manual_chatgen.L5X        historical baseline (see below)
```

- `{version}` is `JARVIS_VERSION` from `src/lib/agentGenerator/jarvisVersion.js`
  (logged in `docs/JARVIS_VERSIONS.md`).
- The harness **never overwrites** an existing benchmark for the same version —
  repeat runs get `-2`, `-3`, ... suffixes.
- Usage: `node scripts/jarvisBenchmark.cjs <projectFile> [smNameOrId]`
  (omit the SM to list a project's state machines).

## The three eras

**(A) Old rule generator — pre-standard.**
The deterministic exporter (`src/lib/l5xExporter.js`) building L5X from
hardcoded rules, written before the SDC V4.2 standard templates existed. Its
output is archived as-is; its defects are the data — do not fix them.
Example: `SDC_Servo_PNP/__oldgen_april2026_baseline.L5X` (April 2026 rule-engine
output for the Servo PNP station).

**(B) Old rule generator + new V4.2 templates — this era does not exist.**
The rule engine cannot consume the V4.2 standard templates at all: it has no
mechanism to read a template L5X and conform to it — every pattern it emits is
hardcoded. Adopting the new standards with the rule engine would have meant
rewriting the generator by hand for every template revision. The absence of
this era is the core argument for JARVIS: an AI layer that takes the templates
as law can track the standard without a code rewrite per revision.

**(C) JARVIS versions.**
The AI generation layer (`src/lib/agentGenerator/` + `POST /api/generate`).
Since v1.0.1 (surgical merge): the model authors a JSON edit plan only; a
deterministic merge engine applies it to the V4.2 template (BOM/CRLF/L5K
string LEN all preserved); validation adds a diagram-vs-code cross-check
(`validateAgainstDiagram`); failures feed back to the model for up to
`JARVIS_MAX_ATTEMPTS` total calls. Default model `claude-opus-5`
(`claude-fable-5` is the quality escalation path). Each output is stamped
`Generated by JARVIS v{version}` and archived here per version so quality is
comparable release to release.
`SDC_Servo_PNP/__jarvis_v0_manual_chatgen.L5X` is the proto-JARVIS data point:
Claude-in-chat generation against the V4.2 templates before the endpoint
existed (hence "v0" — same idea, no pipeline).

## Results

| JARVIS | Benchmark | Result | Attempts | Duration | Tokens (in/out) | Cost | Notes |
|--------|-----------|--------|----------|----------|-----------------|------|-------|
| 1.0.0 | SDC_Servo_PNP | FAIL | 1 | ~14 min | — / 100K (cap) | ~$6 | Model wrote the whole L5X; truncated at the 100K output cap — architecture abandoned |
| 1.0.1 | SDC_Servo_PNP / SDC_Servo_PNP | **PASS** | 1 | 307s | 1.7K+25K cache / 31K | $0.94 | 68-op edit plan; 0 validation errors; 0 diagram cross-check defects; 4 *Replace notes for the CE |
| 1.0.1 | 996-Magnet_Dial_AI / Magnet_Feed | **PASS** | 3 | 819s | 16K+54K cache / 82K | $2.48 | Attempts 1-2 truncated at 32K output (plan too verbose); truncation feedback produced a compact 91-op plan on attempt 3; 0 errors, 0 defects; 5 *Replace notes |

Model: claude-opus-5 for both v1.0.1 runs. Cost = real usage tokens x list
pricing (cache writes/reads included), from `costEstimate` in each report.
